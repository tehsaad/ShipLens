# Handover

Operational notes for running the platform: setup, configuration, sample data, deployment, a
runbook and the known limitations. Architecture decisions are in
[architecture/](architecture/README.md), every server action and route in [api/](api/README.md),
and the role × action table in [permissions.md](permissions.md).

## Setup

The [README](../README.md#local-setup) has the full local setup. In short:

1. Install Node.js 24 (`.nvmrc`), then run `npm ci`.
2. Copy `.env.example` to `.env` and fill in `DATABASE_URL`, `AUTH_SECRET` and
   `TEST_DATABASE_URL`.
3. Start PostgreSQL 16 (`docker compose up -d`), apply the migrations (`npm run db:deploy`)
   and load the sample data (`SEED_DEMO_PASSWORD=… npm run db:seed`).
4. Run `npm run dev` and open <http://localhost:3000/en> or <http://localhost:3000/admin>.

## Environment variables

| Variable                   | Production (Render)                                 | Local                           | Secret |
| -------------------------- | --------------------------------------------------- | ------------------------------- | ------ |
| `DATABASE_URL`             | From the `shiplens-db` database (`render.yaml`)     | `.env`                          | Yes    |
| `AUTH_SECRET`              | Generated by Render                                 | `.env`, 32+ random characters   | Yes    |
| `AUTH_TRUST_HOST`          | `true`                                              | `true`                          | No     |
| `TRUSTED_CLIENT_IP_HEADER` | `cf-connecting-ip`                                  | Unset (first `X-Forwarded-For`) | No     |
| `SEED_DEMO_PASSWORD`       | Set in the Render dashboard while demo logins exist | Shell, for `npm run db:seed`    | Yes    |
| `SITE_URL`                 | Unset: defaults to `https://shiplens.onrender.com`  | Optional; a bare HTTPS origin   | No     |
| `DATABASE_MIGRATION_URL`   | Unset (the app connects as the database owner)      | Optional                        | Yes    |
| `TEST_DATABASE_URL`        | Not used                                            | Integration tests               | No     |
| `E2E_DATABASE_URL`         | Not used                                            | End-to-end tests                | No     |

Secrets live only in Render's environment and in local `.env` files, which git ignores. The
server validates `DATABASE_URL`, `AUTH_SECRET` and `TRUSTED_CLIENT_IP_HEADER` at start and
exits if they are invalid. GitHub holds one secret, `RENDER_DEPLOY_HOOK_URL` (see
[Deployment](#deployment)).

## Sample data and demo logins

`npm run db:seed` loads the sample data from `docs/SPEC.md` section 10: 6 branches (4 ACTIVE,
1 FORMING, 1 PAUSED), one user per staff role plus one Branch Lead per branch, 40 members in
teams, 20 applications, 120 collections over the 12 months ending 18 October 2026, 8 weekly
reports, 6 published content entries, 2 events and 1 contact message.

- Values and dates are fixed, so every run produces the same data.
- The script is safe to re-run: it creates only missing records and never overwrites
  existing ones, including passwords.
- Every demo account uses the password in `SEED_DEMO_PASSWORD` (at least 12 characters).
- On Render (and in the Docker image generally) the container runs the seed at every start
  while `SEED_DEMO_PASSWORD` is set. Remove the variable to stop seeding, for example once the
  demo accounts are retired; existing data is never touched either way.
- Demo accounts do not have to change their password on first sign-in, so the published
  credentials keep working (decision 5a). Accounts created any other way always must.

## Database roles

Migrations create a `NOLOGIN` role, `shiplens_app`, with the privileges the application
needs. It has no `UPDATE` or `DELETE` on `audit_logs` (section 5), and no `DELETE` anywhere
except team assignments. To run the app with these restricted privileges:

1. Run migrations as the database owner (`DATABASE_MIGRATION_URL`).
2. Create a login role for the app:
   `CREATE ROLE hamqadam_web LOGIN PASSWORD '<strong password>' IN ROLE shiplens_app;`
3. Point `DATABASE_URL` at that role.

If the migration user may not create roles, the migration skips this step. Database triggers
still enforce the append-only audit log, the 7-day collection lock, and the other rules.

## Security operations

The full OWASP mapping is in [security.md](security.md).

- **Rate limits are per instance.** Failed sign-ins (10 per 15 minutes), the volunteer
  application and the contact form (5 per hour each) are counted per client IP in the
  server's memory.
  - With more than one instance, each counts separately; a shared store (for example Redis)
    would be needed. A restart clears the counters.
  - The per-account lockout (5 failures, 15 minutes) is stored in the database and is not
    affected.
- **Logs.** The server writes one JSON object per line: server errors (`request.failed`, with
  the digest shown on the error page), exports, rate-limit refusals and health-check
  failures. Each line has a `requestId`.
  - On Render they are in the service's Logs tab.
  - Search for a digest a user reports, or for `"event":"request.failed"`.
- **Audit log.** Super Admins read it at `/admin/audit`. Every change and every export is
  there; filter the action by `export` to see who downloaded what.
- **Dependencies.**
  - CI fails when a production dependency has a high or critical advisory.
  - Dependabot opens weekly update pull requests, each of which must pass CI before merging.
  - Turn on Dependabot alerts and security updates in the repository settings
    (Settings → Code security).

## Tests

| Command                    | What it runs                                                        |
| -------------------------- | ------------------------------------------------------------------- |
| `npm run test:unit`        | Unit tests (rules, permissions, validation, CSV, PDF, headers)      |
| `npm run test:integration` | Services, database rules and the seed against `TEST_DATABASE_URL`   |
| `npm run test:coverage`    | Both of the above; fails below 60% of backend lines (section 11)    |
| `npm run test:e2e`         | Playwright: each role's refusals, the report cycle, axe on the site |

CI runs all of them on every push and pull request (`.github/workflows/ci.yml`).

### End-to-end tests

The suite (`e2e/`) runs against the production build, not the dev server:

1. Create an empty, throwaway database and set `E2E_DATABASE_URL` to it. Every run drops and
   recreates its schema, so never point it at data you want to keep.
2. `npm run e2e:prepare` builds the app and the seed script. Run it again after code changes.
3. `npm run test:e2e`. `scripts/e2e-server.mjs` applies the migrations, loads the sample data
   with a fixed test password and starts the standalone server on port 3200, as the container
   does at start. It reads no `.env` file.

The first run needs a browser: `npx playwright install chromium`. Where a Chromium is already
installed, set `PLAYWRIGHT_CHROMIUM_PATH` to its executable instead. A failed run leaves
screenshots and traces in `test-results/` (`npx playwright show-trace <trace.zip>`); in CI they
are kept as the `playwright-report` artifact for a week.

## Deployment

The service deploys `main` only, and only after CI passes on it:

1. A push to `main` (normally a merged pull request) runs CI.
2. When CI succeeds, the `Deploy` workflow (`.github/workflows/deploy.yml`) calls the Render
   deploy hook with `ref=<commit>`, so Render deploys exactly the commit CI tested.
3. Render builds the image; the container applies migrations, loads any missing sample data
   (while `SEED_DEMO_PASSWORD` is set) and starts. Render switches traffic once
   `GET /api/health` answers 200.

**The deploy hook is a secret.** Anyone with the URL can trigger a deploy. It is stored as the
repository secret `RENDER_DEPLOY_HOOK_URL` (Settings → Secrets and variables → Actions). To
rotate it: in Render open the service → Settings → Deploy Hook → regenerate, then paste the new
URL into the GitHub secret.

**Deploying by hand.** In Render, open the service → Manual Deploy → Deploy latest commit (or
a specific one). Use this to redeploy after a change of environment variables, or if the
`Deploy` workflow cannot reach Render. Re-running a failed `Deploy` workflow run in GitHub
retries the hook for the same commit.

**Rolling back.** In Render, open the service → Events, pick an earlier successful deploy and
choose Rollback. Migrations are not reversed by a rollback, so a migration that is not
backward compatible needs a follow-up migration instead.

## Runbook

**The site is down, or `/api/health` answers 503.**

1. Open `https://shiplens.onrender.com/api/health`.
   - `{"database":"down"}` means the app runs but cannot reach PostgreSQL. Check the database
     in Render: its status, and whether a free database has expired.
   - No answer at all: the free web service may be waking from sleep, which takes up to a
     minute. Check the service's Events and Logs in Render.
2. A deploy that fails its health check never receives traffic: the previous version keeps
   serving. Read the failed deploy's logs.

**A deploy failed.**

- **Failed in CI:** nothing was deployed. Fix the change on a branch and merge again.
- **Failed in Render:** read the build or start logs. A failing migration stops the container
  before it serves, so the previous version stays live.

**Roll back.** In Render, open the service → Events, pick the last good deploy and choose
Rollback. Migrations are not undone (see [Deployment](#deployment)).

**A staff member is locked out or forgot their password.**

- A lockout clears by itself after 15 minutes.
- A Super Admin can reset the password from `/admin/users/<id>`: set a temporary password,
  which the user must change at next sign-in.
- If every Super Admin is locked out, wait the 15 minutes, or use a database session to clear
  `locked_until` for that user.

**Someone should lose access now.** Deactivate the account on `/admin/users/<id>`. The next
request from that user is refused, even with a valid session cookie.

**Rotate secrets.**

- **`AUTH_SECRET`:** change it in Render and redeploy. Every user is signed out.
- **Demo password:**
  1. Change `SEED_DEMO_PASSWORD` in Render. This affects only accounts created later.
  2. Reset each demo account's password from the Users screen, or deactivate the demo
     accounts.
- **Deploy hook:** regenerate it in Render, then update `RENDER_DEPLOY_HOOK_URL` in GitHub.
- **Render API keys:** delete keys that are no longer needed (Render → Account Settings → API
  Keys).

**Find what went wrong for a user.**

- An error page shows a digest. Search the Render logs for that digest, or for
  `"event":"request.failed"`. Each line carries a `requestId`.
- Who changed or exported what is in `/admin/audit` (Super Admin).

**Database.**

- Render keeps backups of paid databases only. On the free plan, take a manual backup with
  `pg_dump` (the external connection string is in the Render dashboard) before risky
  changes.
- The audit log cannot be edited or truncated, even by the app's own role.

## Known limitations

- **Single instance.** The rate limiter keeps its counters in memory. With more than one
  instance, each counts separately, and a restart clears them. A shared store such as Redis
  would be needed (see [Security operations](#security-operations)).
- **Urdu in PDFs.** PDFs use the standard PDF fonts, so Urdu typed into a note prints as "?".
  Screens and CSV exports show it in full ([ADR 0009](architecture/0009-pdf-generation.md)).
- **Urdu page speed.** The Nastaliq font is about 230 KB. Urdu pages score lower in Lighthouse
  mobile performance than English pages ([ACCEPTANCE.md](ACCEPTANCE.md)).
- **Free hosting plan.** The web service sleeps when idle, so the first request after a pause
  is slow. A free database is kept for a limited time, and has no automatic backups.
- **Demo accounts.** They share one known password and do not have to change it at first
  sign-in (decision 5a). Rotate or deactivate them before real use.
- **Admin language.** The admin area is in English; only its navigation labels are
  translated (section 7.4).
- **Interface choices.** Tables cannot be re-sorted in the browser
  ([ADR 0010](architecture/0010-tables.md)). Dashboard figures follow the current date, so
  they differ from `docs/sample-data-expected.md` on any day other than 18 October 2026.
